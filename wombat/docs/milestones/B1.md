# Milestone B1: a minimal bridge between Flutter and the Rust core

("Milestone B1" is the bridge work of `NEXT_BRIDGE.md`. It is not decision B1, "Links point at
cell IDs", in section B of `DECISIONS.md`.)

Status: **built, run on Linux, and built for Android; not finished by the brief's
definition.** What is left needs an Android device and a session that did not write this, and
is listed under "Left to do": running the app on Android, the measurements there, and the
independent review. Everything else that `NEXT_BRIDGE.md` asks for is here and passes.
Decisions A122 to A131 are new; there are no new departures from TreeSheets, so nothing was
added to section B. The file format did not change.

A bare Flutter app now opens a real Wombat document through the Rust core, shows it as text,
changes one cell, shows what the core says changed, and undoes it.

## What was built

- **Three additions to the core**, each with tests (`crates/wombat-core/tests/read.rs`):
  - `Editor::grid_view`: one cell and the cells of its grid, each with its text, kind, what a
    formula cell shows, whether that is an error value, and whether it has a grid (A125).
  - `Clip::as_document` and `Clip::from_document`: a clip leaves the program as a document
    and comes back checked, so that the two paste commands can be serialised without opening
    a way to make cells that break the model's rules (A124).
  - A test that `Editor`, `Clip`, `Command` and `Error` can move between threads.
- **The bridge crate** `crates/wombat-bridge` (package `wombat_bridge`), about 1,800 lines
  written by hand and 3,300 generated:
  - `api/document.rs`: `OpenDocument`, the handle Dart holds. Open a file, create one, open
    a copy with fresh IDs; the ID of the document and of its root; read one grid; apply one
    command; undo; redo; save. Every one returns a value or an error value.
  - `api/wire.rs`: the serialised form of all 45 commands, of change reports (with the
    recalculated formula cells, A126) and of errors (A123, A129).
  - `convert.rs`: between that form and the core's types, checking on the way in.
  - `record.rs`: the same form as JSON text, to record commands and play them back.
- **The bare app** `app/`: one screen of plain text and three buttons, Open, Change and Undo.
  Open copies the example that comes with the app (`assets/example.wombat`, 14 cells, two
  nested grids and a formula) and prints the root grid and the grids inside it. Change sets
  the text of one cell and prints the change report and the grids again. Undo undoes.
- **Tests without a device**, in both languages (see "Tests"), and a second job in
  `.github/workflows/wombat.yml` that runs the Dart ones.

## How to try it

On a machine with Rust (rustup) and Flutter 3.47.9. On Linux the desktop build also needs
`libgtk-3-dev`.

```sh
cd wombat
cargo test -p wombat_bridge          # the Rust side
cargo build -p wombat_bridge         # the library the Dart test loads
cd app
flutter pub get
flutter test                         # the Dart side, calling the real core
flutter run -d linux                 # the app; press Open, Change, Undo
```

On a machine without a screen, the real app is run and its buttons pressed by:

```sh
xvfb-run -a flutter test integration_test -d linux
```

A recorded command looks like this (`record::command_to_json`):

```json
{"SetText": {"cell": "00000000-0000-0000-0000-000000000001", "text": "new"}}
```

## Tests

`cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings` and
`cargo test --workspace` pass with the new crate in the workspace.

- **Core** (`tests/read.rs`, 9 tests): the grid view by example (formula result, error value,
  nested grid, no grid, no such cell) and by rule on documents that random commands made
  (the view agrees with the document and with `Editor::shown` for every cell); every clip of
  every cell of such documents comes back equal through a document and through its text;
  what a clip cannot be is refused, and its source is the ID of the document it comes back
  from.
- **Serialised form** (`crates/wombat-bridge/tests/roundtrip.rs`, 8 tests): 2,000 random
  commands, drawn from all 45 with any values in their fields, come back unchanged through
  the mirror types and through JSON. A test checks that the generator makes every one of the
  45, and its list does not compile when the core gains a command. Reports and errors
  survive JSON. Text that is no command, an ID not in canonical form, a scale that is not
  finite, unknown fields that are no JSON object, a table without whole rows and a clip that
  was tampered with are each refused as a value. The JSON form is pinned by example.
- **The sequence** (`crates/wombat-bridge/tests/session.rs`, 7 tests): what the app does, on
  a copy of the same example: open, read the root grid and one inside it, set a text, check
  the report (the cell, and the formula that reads it), undo, redo, save, open again. Also
  creating, copying, the clock, each kind of error with the document left as it was, and
  playing recorded commands back.
- **Dart, without a device** (`app/test/demo_test.dart`, 3 tests): the same sequence through
  the generated bindings and the real library, fresh IDs of the copy, and errors arriving as
  `BridgeError` with their kind.
- **Dart, the real app** (`app/integration_test/app_test.dart`): presses the three buttons
  and reads the screen.

## Measurements (Linux desktop)

Taken by `app/lib/measure.dart` through `app/integration_test/measure_test.dart`, on the
Linux x86-64 cloud machine (4 cores, under Xvfb, software rendering), in **profile mode**:
Dart compiled ahead of time, the Rust library built with `--release`. **These are desktop
numbers, not phone numbers.** A debug build is about three to four times slower and is not
shown.

The document is the shape of the one in `crates/wombat-core/tests/large.rs`: 101,001 cells,
a root grid of 10 by 100 whose cells each hold a grid of 10 by 10, 12.9 MB as a file. It is
built on the spot with one `Import` command. One innermost cell holds a formula that reads
every cell of the document, so that an edit includes a recalculation; a second pass without
that formula shows what the command and the bridge cost alone. Each timing is 5 runs in
one process; two separate processes agreed within a few percent, and the first is shown.

| Step, end to end from Dart | Median | Worst |
| ---- | ---- | ---- |
| Open the document | 615 ms | 690 ms |
| Read the root grid (1,000 cells) | 2.9 ms | 4.2 ms |
| Read an inner grid (100 cells) | 1.5 ms | 1.7 ms |
| Set the text of one cell, with the formula | 40.5 ms | 41.2 ms |
| Insert a row in the root grid, with the formula | 78.6 ms | 83.0 ms |
| Set the text of one cell, no formula | 1.4 ms | 1.4 ms |
| Insert a row in the root grid, no formula | 1.4 ms | 1.6 ms |
| Save | 207 ms | 229 ms |

Undoing each edit takes as long as the edit.

| Resident memory of the app | MiB |
| ---- | ---- |
| Before opening (the app alone) | 208 |
| After opening | 381 |
| Peak while opening | 414 |
| At the end, after 5 opens, the edits and 5 saves | 752 |

What they say:

- **The bridge itself costs about a millisecond a call.** An edit that nothing depends on is
  1.4 ms from Dart and back.
- **Opening takes about 0.6 s**, against 0.38 s for the core's load alone in milestone 1:
  opening also checks the document and works out the formulas.
- **Opening costs about 206 MiB at its peak over what the app takes alone, for a 12.9 MB
  file: about 16 times the file.** A file at the 32 MiB limit would be near 500 MiB, which
  many phones do not give an app. This is the known concern of `POC_SUMMARY.md`, now with a
  number from inside an app. Nothing was done about it here.
- **An edit is slow when a formula reads the whole document:** 40 ms for a text, 80 ms for
  a row, nearly all of it recalculating (`M5.md`: everything is worked out again after a
  structural change). 80 ms is five frames at 60 Hz on a desktop processor; a phone will be
  slower. The calls run off the thread that draws, so the screen does not freeze, but the
  result arrives late.
- **Memory grows when a document is opened again and again in one process** (381 MiB after
  one open, 650 to 750 after five). It did not look like a leak: with glibc told to use one
  arena (`MALLOC_ARENA_MAX=1`) a throwaway run stayed level over eight opens. glibc keeps a
  heap per worker thread. Android has a different allocator, so look at this there.

## Not verified

- Anything running on Android or iOS, on a phone, or under real memory limits. Loading peaks at
  about 13 times the size of the file (`POC_SUMMARY.md`); on a phone a document near the
  32 MiB limit may be killed by the system, which no error value can report. No lower limit
  was set here.
- That generated code is up to date is not checked by CI: it would need the generator
  installed there. Regenerate after every change to `api/` (`../AGENTS.md` says how).
- macOS and Windows desktop builds. `rust_builder/` has their build files as
  `flutter_rust_bridge` generated them; the app was created for Linux and Android only.
- Calls that overlap. Dart awaits each call in the app and the tests; that two calls on one
  document made at once queue up, as `flutter_rust_bridge` documents, was not tried.
- A panic crossing the bridge was tried once in a throwaway project (A129), not by a test
  here.

## What went wrong, and what the next piece of work should know

- **The build of the app does not use the pinned Rust.** cargokit compiles the bridge with
  rustup's `stable`, whatever `rust-toolchain.toml` says (A131). On this machine the two
  were the same version. A newer stable can warn where the pin does not; warnings do not
  fail that build.
- **The package had to be named with an underscore** (A131), or the app fails at link time
  with "cannot find -lwombat_bridge".
- **Freezed.** Enums that carry data, such as `Command`, become Dart sealed classes through
  the `freezed` package, which the generator needs in `pubspec.yaml` (`freezed_annotation`,
  and `freezed` and `build_runner` as dev dependencies). Without them it stops half-way with
  a long backtrace.
- **Flutter's own names.** The mirror types avoid `Color`, `TextAlign`, `Table`, `Clip` and
  `GridView`, which Flutter has: they are `Rgb`, `HorizAlign`, `TableData`, `ClipData` and
  `GridInfo` here.
- **Every call is asynchronous**, also `id()` and `root()`: a synchronous call on a document
  that another call is working on would block the thread that draws.
- **Reading is one grid at a time.** The app reads the root grid and then each grid inside
  it with a call of its own. The real grid screen will want the cells it can show, which
  the core cannot answer cheaply yet; `NEXT_BRIDGE.md` leaves that to the next piece.
- **Dart cannot get a clip yet.** The paste commands are in the serialised form, but no call
  gives a clip to Dart (`convert::clip_out` exists on the Rust side). Copy and paste need it.
- **Typing and groups are not bridged** (`apply_typing`, `begin_group`, `end_group`), nor
  search, links, the program's report, import from a file or export.

## Fixes after review

The independent review (`../NEXT_REVIEW.md`) found the following. Each fix began with a test
that failed because of the finding.

- **A clip carried its source twice** (finding 5, A132). `ClipData.source` and the ID of the
  carried document could differ, and `source` won silently. Test:
  `the_source_of_a_carried_clip_is_the_id_of_its_document` (`roundtrip.rs`) carries the same
  cells as a document with another ID and expects that ID as the source; it failed with the
  old one. `ClipData.source` is gone and `Clip::from_document` takes two arguments. In the
  core, `tests/read.rs` pins the source, and builds two unchecked documents whose clips
  `Clip::as_document` must refuse, so the check there is not dead code as the review
  suspected.
- **One kind of error meant two things** (finding 8, A133). `ErrorKind::Invalid` was both a
  broken file and a malformed request. Tests: `what_cannot_be_a_command_is_refused_as_a_value`
  and the two session tests (Rust and Dart) now expect `BadRequest` for what the bridge
  refuses and `Invalid` for what the core does; they did not compile before the kind existed.
  A list of every kind, which does not compile when one is added, replaces the hand-kept
  list of the JSON test.
- **Whole numbers from Dart were cut to 32 or 8 bits without a word** (finding 2, A134).
  Test: `app/test/wire_test.dart` asks for a row inserted at 4294967296 and expects
  `BadRequest`; before, the row was inserted at 0. In Rust, `numbers_out_of_range_are_refused`
  goes through the edges of each range, and `every_number_of_a_command_is_checked` puts a
  number out of every range into each whole number of random commands in turn. The mirror
  types carry `i64` and `convert.rs` checks the range.
- **A deeply nested table to import ended the process** (found by the evaluation after the
  review, A135). The serialised form was a table within a table, and the generated decoder
  and the conversion recursed without a bound: a stack overflow, which no error value or
  caught panic reports. Tests: `crates/wombat-bridge/tests/deep.rs` converts a table nested
  100,000 deep on a 2 MiB stack and expects `Limit` (it aborted the test process before),
  and `app/test/wire_test.dart` imports one through the real library (the Dart test process
  died at depth 5,000 before). The form is now one flat list; `measure.dart` builds its
  document in that form.
- **The generated file was let off more lints than it needs** (evaluation, A122). `lib.rs`
  allowed six for `frb_generated`; only `unsafe_code` and `clippy::unwrap_used` are needed.
  Checked with clippy: it passes with the two, and fails without either. A122 named
  `missing_docs` wrongly and is corrected.
