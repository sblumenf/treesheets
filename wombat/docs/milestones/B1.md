# Milestone B1: a minimal bridge between Flutter and the Rust core

("Milestone B1" is the bridge work of `NEXT_BRIDGE.md`. It is not decision B1, "Links point at
cell IDs", in section B of `DECISIONS.md`.)

Status: **built, run on Linux and on an Android emulator in CI, reviewed four times, and
widened for the first screen of the interface (plan step 1); not finished by the brief's
definition.** What is left needs an Android phone and is listed under
"Left to do": running the app on one and the measurements there. Four independent reviews
were done, each of what the one before had led to: of the bridge, of the fixes to it, of the
Dart side of those fixes, and of the Dart layers that the real interface will be built on.
What each found and what was done about it is under "Fixes after review", and what is still
open after all four under "Still open after the fixes".
Everything else that `NEXT_BRIDGE.md` asks for is here and passes. Decisions A122 to A131
are from the milestone, A132 to A148 from the first review and the evaluation after it,
A149 to A153 from the second review, A154 to A159 from the third and A160 to A163 from the
fourth; A164 and A165 are the owner's (the application ID, and where documents are kept).
After the reviews the core, the bridge and the Dart layers that are kept were widened for
the first screen of the interface: one read of the stage and everything nested below it,
groups of commands that can be cancelled, the view state of the device, line breaks in
cell text, and in Dart the stage kept up to date, the editing of a cell and the editor as
an exchangeable part. That is "For the first screen (plan step 1)" under "What was
built", and decisions A166 to A180. Nothing of it was reviewed independently.
The document format is still version 1.0, changed in place (a cell's text may hold line
breaks, A174); the view-state format is version 1.1 (A172).

**Since this page was written** the first slice of the interface was built (`UI2.md`,
decisions A181 to A190) and the stand-in grid screen removed. Where this page names a
test in `app/test/stage_test.dart`, `grid_screen_test.dart` or `grid_screen_real_test.dart`,
or code in `app/lib/grid/`, that file is gone: the record of what was found and fixed

**How to read this page.** "What was built", "Tests" and "Not verified" say how things are

A Flutter app now opens a real Wombat document through the Rust core, shows one grid of it
at a time, edits the text of a cell with undo and redo, and keeps the document in its file
without being asked. The bare screen that the milestone asked for (the document as text,
one cell changed, what the core says changed, undo) is still there as a check.

## What was built

- **Three additions to the core**, each with tests (`crates/wombat-core/tests/read.rs`):
  - `Editor::grid_view`: one cell and the cells of its grid, each with its text, kind, what a
    formula cell shows, whether that is an error value, and whether it has a grid (A125).
  - `Clip::as_document` and `Clip::from_document`: a clip leaves the program as a document
    and comes back checked, so that the two paste commands can be serialised without opening
    a way to make cells that break the model's rules (A124).
  - A test that `Editor`, `Clip`, `Command` and `Error` can move between threads.

  After the first review the storage layer gained what an open document needs to know
  about its file: `FileState` and `FileState::check` (A138), and a copy that removes what
  it made when it fails (A139).
- **The bridge crate** `crates/wombat-bridge` (package `wombat_bridge`), about 2,900 lines
  written by hand and 3,500 generated (`frb_generated.rs`):
  - `api/document.rs`: `OpenDocument`, the handle Dart holds. Open a file, create one, open
    a copy with fresh IDs; the ID of the document, of its root, and its path from the root
    (A149); whether anything is unsaved; read one grid; apply one command; undo; redo;
    save, which looks at the file first and never goes over another program's work (A140);
    overwrite; close (A142). Every one returns a value or an error value. A file is open in
    one document at a time (`open_files.rs`; A141, A150), a document that is dropped
    unclosed is saved if that is safe (A142), and one that a panic may have left half
    changed is not used again (A143).
  - `api/wire.rs`: the serialised form of all 45 commands, of change reports (with the
    recalculated formula cells, A126) and of errors (A123, A129), with whole numbers in 64
    bits (A134) and a table to import as one flat list (A135).
  - `convert.rs`: between that form and the core's types, checking on the way in.
  - `record.rs`: the same form as JSON text, to record commands and play them back; only
    the form that is written is read (A136, A152).
- **The app** `app/`:
  - `lib/session.dart`: `Session`, the one Dart class through which the app and its tests
    reach a document, which sends the calls in the order they were made (A144), and
    `InTurn`, the queue that does it (A154, A160).
  - `lib/keeper.dart`: `Keeper`, which owns the open document for every screen on it, is
    the one place that saves, and says how the document stands with its file (A145, A155,
    A159, A161).
  - A simple grid screen (`lib/grid/`, described in `UI1.md`), which was what the app
    started with until the phone screen replaced it (`lib/phone/`, `UI2.md`), on one
    document that it keeps between starts in its own data folder (`lib/main.dart`; A163,
    A165), and whose exit waits for the document (A162).
  - The bare screen that this milestone was first shown with, now the "Bridge check" in
    the menu (`lib/demo.dart`, `lib/demo_screen.dart`): plain text and three buttons, Open,
    Change and Undo. Open copies the example that comes with the app
    (`assets/example.wombat`, 14 cells, two nested grids and a formula) and prints the root
    grid and the grids inside it. Change sets the text of one cell and prints the change
    report and the grids again. Undo undoes.
  - `lib/measure.dart`, which times the bridge on a document of 101,001 cells.
- **For the first screen (plan step 1)**, after the four reviews. No screen was built in
  that step; the screen came after it (`UI2.md`).
  - *The core.* `Editor::stage_view` and `Editor::cell_look` (`edit/stage.rs`, A166): the
    stage grid or a window of it, the trail, the grids nested below cell by cell as deep
    and as large as asked, and a summary of every grid met (size, preview texts, shape
    bytes), in one flat answer and in proportion to what is asked. `Editor::retype`
    (A169), which makes a cell's text the text of an editor by replacing only what differs
    (`text::difference`, A168), so that a bold word and a link elsewhere in the cell stay;
    through `SetText` or `EnterText` both were lost. `Editor::cancel_group` (A170): an
    open group taken back as if it had not been (document, undo and redo history, size
    bound); what could be redone is now kept while a group is open and goes when the group
    ends. `Editor::audit`, which lets the tests count the editor's bookkeeping again.
    `ViewState` gained `levels` (A172): per level the column and row at the top left of
    what was last seen and the selected cell, at most 256; `stage` never names a cell that
    is not in the document, and when the level that is shown is removed the zoom moves to
    the nearest level above that is left (it went to the root before). **Line breaks in
    cell text** (A174, the owner's decision): U+000A is kept, CR LF and CR become one,
    every other control character still becomes a space; through every command, formulas,
    search and replace, import and export, and the command-line tool.
  - *The bridge* (A167, A171, A173). `OpenDocument` gained `stage(cell, ask)` and
    `cell(cell)`; `begin_group`, `end_group`, `cancel_group`, `in_group` and `retype`;
    `view_stage`, `view_go`, `view_remember`, `set_folded`, `is_view_saved` and
    `save_view`. The entries of a stage read compare as values in Dart. A cancelled group
    leaves a saved document saved. The view state is read at opening, kept in step with
    every report and written to its own file after the document; its file can never fail
    or delay the saving of a document.
  - *The Dart layers that are kept* (A175 to A180). `Session` carries the new calls in
    order, with `units` (the way back from the core's code points to a Dart string's
    offsets) and `phoneAsk`. `Keeper` has, for every screen: `read`, which gives a
    `StageReader` that the keeper reads again after every change and that tells what
    differs, cell by cell (`lib/stage_read.dart`); `edit`, which gives an `Editing` with
    `hold`, `style`, `enter` and `drop`, so that nothing is sent while the user types, one
    editing is one step of the undo history and the cross is exact; and the view state,
    written with every save. `lib/cell_editor.dart` is the editor of a cell as a screen
    knows it, with one kind made of Flutter's text field: several lines, Return as the
    screen's action, a line break by `insert`. The stand-in screen used the editing and
    the editor (its own workaround for the cross, A157, was gone by then), as the phone
    screen does now, and the stand-in for the core in the tests is held to the real core
    (A179).
- **Tests without a device**, in both languages (see "Tests"), and CI in four jobs
  (`.github/workflows/wombat.yml`): the Rust checks; the generated code compared with what
  the generator writes, the Dart checks and tests, and the built Linux app run by its
  integration tests; the debug package for Android arm64, built and not run; and, since
  the fourth review, the integration tests on an Android emulator.

## How to try it

On a machine with Rust (rustup) and Flutter 3.47.9. On Linux the desktop build also needs
`libgtk-3-dev`.

```sh
cd wombat
cargo test -p wombat_bridge          # the Rust side
cd app
flutter pub get
flutter test                         # the Dart side, calling the real core
flutter run -d linux                 # the app; the bare screen is "Bridge check" in the menu
```

(`flutter test` builds the bridge's library itself before it loads it, with
`cargo build -p wombat_bridge`; see `app/test/support.dart`.)

On a machine without a screen, the real app is run and its buttons pressed by:

```sh
xvfb-run -a flutter test integration_test/app_test.dart -d linux
```

One file for each run: the whole folder at once (`flutter test integration_test -d linux`)
fails with "Error waiting for a debug connection" since there is more than one file in it.
All of them, as CI runs them:

```sh
for test in integration_test/*_test.dart; do xvfb-run -a flutter test "$test" -d linux; done
```

A recorded command looks like this (`record::command_to_json`):

```json
{"SetText": {"cell": "00000000-0000-0000-0000-000000000001", "text": "new"}}
```

## Measurements (Linux desktop)

Taken by `app/lib/measure.dart` through `app/integration_test/measure_test.dart`, on the
Linux x86-64 cloud machine (4 cores, under Xvfb, software rendering), in **profile mode**:
Dart compiled ahead of time, the Rust library built with `--release`. **These are desktop
numbers, not phone numbers.** A debug build is about three to four times slower and is not
shown.

The document is the shape of the one in `crates/wombat-core/tests/large.rs`: 101,001 cells,
a root grid of 10 by 100 whose cells each hold a grid of 10 by 10, 12.9 MB as a file. It is
built on the spot with one `Import` command. One innermost cell holds a formula that reads
every cell of the document, so that an edit includes a recalculation; a second pass without
that formula shows what the command and the bridge cost alone. Each timing is 5 runs in
one process; two separate processes agreed within a few percent, and the first is shown.

| ---- | ---- | ---- |
| Open the document | 615 ms | 690 ms |
| Read the root grid (1,000 cells) | 2.9 ms | 4.2 ms |
| Read an inner grid (100 cells) | 1.5 ms | 1.7 ms |
| Set the text of one cell, with the formula | 40.5 ms | 41.2 ms |
| Insert a row in the root grid, with the formula | 78.6 ms | 83.0 ms |
| Set the text of one cell, no formula | 1.4 ms | 1.4 ms |

| Resident memory of the app | MiB |
| ---- | ---- |
| Before opening (the app alone) | 208 |
| After opening | 381 |
| Peak while opening | 414 |
| At the end, after 5 opens, the edits and 5 saves | 752 |

What they say:

- **The bridge itself costs about a millisecond a call.** An edit that nothing depends on is
  1.4 ms from Dart and back.
- **Opening takes about 0.6 s**, against 0.38 s for the core's load alone in milestone 1:
  opening also checks the document and works out the formulas.
- **Opening costs about 206 MiB at its peak over what the app takes alone, for a 12.9 MB
  file: about 16 times the file.** A file at the 32 MiB limit would be near 500 MiB, which
  many phones do not give an app. This is the known concern of `POC_SUMMARY.md`, now with a
  number from inside an app. Nothing was done about it here.
- **An edit is slow when a formula reads the whole document:** 40 ms for a text, 80 ms for
  a row, nearly all of it recalculating (`M5.md`: everything is worked out again after a
  structural change). 80 ms is five frames at 60 Hz on a desktop processor; a phone will be
  slower. The calls run off the thread that draws, so the screen does not freeze, but the
  result arrives late.
- **Memory grows when a document is opened again and again in one process** (381 MiB after
  one open, 650 to 750 after five). It did not look like a leak: with glibc told to use one
  arena (`MALLOC_ARENA_MAX=1`) a throwaway run stayed level over eight opens. glibc keeps a
  heap per worker thread. Android has a different allocator, so look at this there.

### The read a screen draws from (plan step 1)

Taken after the reviews, by the same `app/lib/measure.dart` in the same way (profile mode,
the same Linux x86-64 cloud machine, 4 processors, under Xvfb; three runs of `flutter drive
--profile`, the middle of five calls in each, the range over the three runs; other work
was running on the machine during the third). The first document is the one above; the
second is the six-level document of the core's own measurement (68,749 cells; the root's
grid 12 by 20, a third of the cells of every grid holding a grid). Both were read from
their files. The request is the one a screen starts from (`phoneAsk`: the whole stage
grid, one level of nested grids cell by cell where a grid has at most 24 cells, previews
of 3 by 4 texts, shapes of 12 by 20 cells) unless said.

| Stage and request | Answer | Whole call from Dart | Dart thread held | Compared with the read before |
| ---- | ---- | ---- | ---- | ---- |
| 101,001 cells: the root, whole | 1,000 cells, 100,000 shape cells | 54–78 ms | 3.4–4.8 ms (worst 8.3) | 6.4–8.9 ms |

"Dart thread held" is the longest time the thread that draws did nothing else while the
call was under way: the decoding of the answer (A127). It is found by a timer that runs
again as soon as it has run, so it includes whatever else held that thread just then; the
"worst" of five is often two or three times the middle. "Compared" is `StageRead.since`
against an equal answer, which is its most work: every cell is compared to its end.

What they say:

- **A stage of the size the interface is specified for costs little**: 11 to 14 ms a read,
  about 5 ms of it on the thread that draws (decoding and comparing). A screen reads it
  again after every change.
- **Nearly all of a large read is the core's shapes**, off the thread that draws (A166:
  about a quarter of a microsecond a shape cell). The bridge's own test timed its Rust side
  at 49 to 60 ms for the first row of the table and 20 to 26 for the second (A167), so
  crossing to Dart and decoding add a few milliseconds.
- **The same document is slower to read a stage of when it was read from its file than
  when it was built in memory**: 48 to 58 ms against 35 to 41 for the core's part of the
  first row, side by side in one process (A167). An app always holds a document read
  from a file. Why was not found out; the guess is that the cells lie in memory in another
  order and each shape cell is one lookup by ID.
- **Two levels cell by cell hold the thread that draws for more than a frame** on a
  desktop (21 to 27 ms for 8,456 cells), so the start is one level.
- **Decided from this** (A176): a reader asks for the whole stage grid unless told; a
  screen that scrolls a window asks for 40 rows (`phoneWindowAsk`) and says which rows it
  shows. A window is worth it from about 400 cells that hold grids.

## What went wrong, and what the next piece of work should know

- **The build of the app does not use the pinned Rust.** cargokit compiles the bridge with
  rustup's `stable`, whatever `rust-toolchain.toml` says (A131). On this machine the two
  were the same version. A newer stable can warn where the pin does not; warnings do not
  fail that build.
- **The package had to be named with an underscore** (A131), or the app fails at link time
  with "cannot find -lwombat_bridge".
- **Freezed.** Enums that carry data, such as `Command`, become Dart sealed classes through
  the `freezed` package, which the generator needs in `pubspec.yaml` (`freezed_annotation`,
  and `freezed` and `build_runner` as dev dependencies). Without them it stops half-way with
  a long backtrace.
- **Flutter's own names.** The mirror types avoid `Color`, `TextAlign`, `Table`, `Clip` and
  `GridView`, which Flutter has: they are `Rgb`, `HorizAlign`, `TableData`, `ClipData` and
  `GridInfo` here.
- **Every call is asynchronous**, also `id()` and `root()`: a synchronous call on a document
  that another call is working on would block the thread that draws.
- **Calls must be sent one at a time.** Two calls on one document that are both under way
  are carried out in either order (A127). `Session` in `app/lib/session.dart` does that for
  the app: use it, and never the handle `OpenDocument` itself (A144). A screen goes through
  the document's `Keeper`, which saves (A155).
- **A test on a stand-in that is not held up tests no ordering.** The stand-in for the
  core answers within the same step of the event loop, so two taps in a widget test end
  one after the other whatever the code does. A test of order or of "nothing is dropped"
  holds the core up (`holdFirst`) or runs on the real core; the third review found four
  faults behind tests that did neither.
- **`tester.enterText` gives a field the focus before it types.** A test that is to show
  that the user can type must use `tester.testTextInput.enterText`, which types into
  whatever has the keyboard.
- **A future made on the test's clock does not move inside `tester.runAsync`.** Widget
  tests on the real core make everything on the test's clock and let real time pass in
  small steps until what they wait for is there (`until` in the tests).
- **Reading was one grid at a time** when this milestone was written, and the stand-in
  screen read so to its end (`Keeper.grid`). Since plan step 1 one read gives the stage
  and what is nested below it (`stage`, A166, A167), and a screen draws from a
  `StageReader` (A176), as the phone screen does.
- **Dart cannot get a clip yet.** The paste commands are in the serialised form, but no call
  gives a clip to Dart (`convert::clip_out` exists on the Rust side). Copy and paste need it.
- **Groups are bridged since plan step 1** (`begin_group`, `end_group`, `cancel_group`,
  `retype`; A171). Still not bridged: `apply_typing` (ruled out: an editor has a text and
  not the keys that made it), search, links, the program's report, import from a file,
  export.
- **What the first screen's author should know** (plan step 1): positions of runs and
  links are code points, not UTF-16 units (`units` in `session.dart`); `==` works on
  `CellLook`, `GridPart`, `GridSummary`, `TrailStep`, `CutText`, `RunInfo`, `LinkInfo` and
  `LevelInfo`, and not on `StageInfo`, and the places inside an answer move
  (`StageRead.since` compares for a screen); the lists of a freezed class are wrapped anew
  at every read of the field, so take `look.runs` once, not in a loop; the text in a cell
  can differ from the text that was sent; `view_remember` on the root of an empty document
  is `Refused`; an error of `save_view` is no save error; a document read from a file
  reads its stage more slowly than the same document built in memory (A167). The rules
  for a screen are in `../../AGENTS.md`.

## Fixes after review

The independent review (`../NEXT_REVIEW.md`) found the following. Each fix began with a test
that failed because of the finding, unless its entry says otherwise.

- **A clip carried its source twice** (finding 5, A132). `ClipData.source` and the ID of the
  carried document could differ, and `source` won silently. Test:
  `the_source_of_a_carried_clip_is_the_id_of_its_document` (`roundtrip.rs`) carries the same
  cells as a document with another ID and expects that ID as the source; it failed with the
  old one. `ClipData.source` is gone and `Clip::from_document` takes two arguments. In the
  core, `tests/read.rs` pins the source, and builds two unchecked documents whose clips
  `Clip::as_document` must refuse, so the check there is not dead code as the review
  suspected.
- **One kind of error meant two things** (finding 8, A133). `ErrorKind::Invalid` was both a
  broken file and a malformed request. Tests: `what_cannot_be_a_command_is_refused_as_a_value`
  and the two session tests (Rust and Dart) now expect `BadRequest` for what the bridge
  refuses and `Invalid` for what the core does; they did not compile before the kind existed.
  A table that is malformed was still `Invalid` then; since the second review it is
  `BadRequest` too (see "The second review" below).
  A list of every kind, which does not compile when one is added, replaces the hand-kept
  list of the JSON test.
- **Whole numbers from Dart were cut to 32 or 8 bits without a word** (finding 2, A134).
  Test: `app/test/wire_test.dart` asks for a row inserted at 4294967296 and expects
  `BadRequest`; before, the row was inserted at 0. In Rust, `numbers_out_of_range_are_refused`
  goes through the edges of each range, and `every_number_of_a_command_is_checked` puts a
  number out of every range into each whole number of random commands in turn. The mirror
  types carry `i64` and `convert.rs` checks the range.
- **A deeply nested table to import ended the process** (found by the evaluation after the
  review, A135). The serialised form was a table within a table, and the generated decoder
  and the conversion recursed without a bound: a stack overflow, which no error value or
  caught panic reports. Tests: `crates/wombat-bridge/tests/deep.rs` converts a table nested
  100,000 deep on a 2 MiB stack and expects `Limit` (it aborted the test process before),
  and `app/test/wire_test.dart` imports one through the real library (the Dart test process
  died at depth 5,000 before). The form is now one flat list; `measure.dart` builds its
  document in that form.
- **The generated file was let off more lints than it needs** (evaluation, A122). `lib.rs`
  allowed six for `frb_generated`; only `unsafe_code` and `clippy::unwrap_used` are needed.
  Checked with clippy: it passes with the two, and fails without either. A122 named
  `missing_docs` wrongly and is corrected.
- **The JSON form took incomplete and misspelt commands** (finding 4, A136). Tests:
  `json_that_leaves_a_field_out_or_adds_one_is_refused` by example (it failed on
  `SetRangeColor` without `color`, which was read as "remove the colour"), and
  `every_field_of_a_command_is_needed_and_no_other_is_read`, which takes each field in turn
  out of random commands as JSON, or adds one. `{"Run": null}` was still read as `"Run"`
  then; since the second review it is refused, with every other form that is read and never
  written (see below). A Dart test shows that `null` still crosses as none.
- **The comments of the serialised form left out rules that the core states** (finding 8).
  They become the documentation of the Dart classes and are all a Dart developer sees. The
  comments of `Command`, `Prop`, `Report` and the types they hold in `api/wire.rs` now say
  what the core's say: control characters become spaces (and, since A174, line ends one
  line break), positions are code points and must
  not cut a user-perceived character, a command that asks for nothing new succeeds with an
  empty report, what each command refuses, the ranges of numbers and the limits. The
  generator drops the comment of an enum that holds data, so those rules are on the
  variants, the fields and `Report` (A137). Nothing
  tests a comment; `cargo doc` with warnings denied resolves every link in them.
- **Half a surrogate pair in a Dart string arrives as U+FFFD without notice** (finding 6).
  Not changed: Dart's own encoder does it before Rust sees the string, and refusing would
  mean checking every string on the Dart side. It is documented at the top of `api/wire.rs`
  and pinned by `half a surrogate pair arrives as U+FFFD` in `app/test/wire_test.dart`
  (cell text, a note, an ID, a path). That test passed when written: it pins behaviour
  that was there, it did not fail first.
- **Mutations that no test noticed** (finding 7, the part in `convert.rs` and the core).
  `crates/wombat-bridge/tests/out.rs` is new. Each of these was made by hand, seen to fail a
  test, and put back: `removed` filled from `grids`, `tags` always empty, `created` and
  `recalculated` filled from `changed` (`report_out`); `failed` always false (`cell_out`);
  `Limit` as `Refused`, `NewerVersion` as `WrongFormat`, `HalfSaved` as `Io` without a path
  or with the wrong file, `AlreadyExists` without a path (the error mapping, now a list over

## Still open after the fixes

Known after four reviews, and left as it is on purpose or for want of a device, a decision
or a change that was not this work's to make. Nothing in this list is fixed.

What makes the app not ready to be released:

- **What is left of its template's defaults**, which are the owner's to decide: the release
  build is signed with the debug key, and `allowBackup` is not set, which means on. (The
  application ID and the label were set by A164.)
- ~~**CI has not yet run the app as it is now on Android**~~: it has, as the app was
  before the Dart side of plan step 1 (run 43287732049 on `014e06d`, "What was run, and
  where"): the package builds with the `path_provider` plugin, the emulator ran
  `io.github.sblumenf.burrow`, the three test files passed, and the second measurement
  opened the file the first one built. **What CI has not seen is the Dart side of plan
  step 1**, which was not pushed when this was written.
- **Nothing has run on a real phone**, or on iOS at all. The emulator run says that the
  library loads on Android and the tests pass there. Untried: what Android does to the
  app when it is put away (the saving of A145 and A155 was run with the test binding's own
  lifecycle events), the back button and edge swipe, the on-screen keyboard and its
  "next" key, and the measurements on a phone. Nothing was built for iOS: the bridge is
  not compiled for it in CI, only the core and the search service are checked.
- **Windows and macOS were never compiled or run.** On Windows the check whether another
  program changed the file is weaker (length and time only, A138). The library names that
  the Dart tests look for there (`loadBridge`) are written from the conventions of those
  systems, and where `path_provider` puts the document there (A165) is by its
  documentation. Whether Windows asks the app before its window closes (A162) is not
  known.
- **The app has one fixed file** and no way to choose, make, name or share a document. It
  is now in the app's own data folder on every system (A165; before, on Android, in
  `code_cache`, which an update of the app emptied). On a phone no other app can see it.
- **The Android part of `path_provider` is held below version 2.3.0**
  (`path_provider_android: ">=2.2.23 <2.3.0"` in `app/pubspec.yaml`; A165). Version 2.3.0
  was rewritten on JNI and brings a native library (`libdartjni.so`) that is then also
  compiled into the Linux and Windows builds, which need a JDK for it and use none of it.
  That has to be looked at again when the plugin stops serving the older part.
- **The editor's field of several lines has never met a real keyboard**, and three things
  about line breaks could not be tried here ("Not verified" has each): a phone's "next"
  key on such a field, a hardware Return in the built app, and what TreeSheets and a
  spreadsheet make of a file with a break inside a field.

What can still lose or overwrite work:

- **An app that is killed outright loses what is in the editor**, and up to a second of
  entered changes (A145). So does one killed while it is only `inactive`, where the
  editor's text is no longer entered (A155). Closing the window is no longer that (A162),
  where the system asks first; and an exit that takes longer than five seconds is let
  through without knowing what was saved.
- **Two running copies of the app work on one document**: each process has its own set of
  open files (A141), so the second start opens the file the first has open. Neither
  writes over the other: whoever saves second is told that another program changed the
  file. Keeping them apart needs a lock that other processes see.
- **What is being typed is given two seconds to be entered** when the app is put away or
  closed (A161). On a document where a command takes longer (a formula over 100,000 cells
  took 0.14 s on the emulator, so far from it today), the text would not be in the file,
  and the caller is told.
- **A link retargeted onto a file that another document has open** can still be
  overwritten: `overwrite()` ("Keep mine") on the first document writes into the second's
  file; `save()` refuses with `ChangedOnDisk` (A150).
- **The gap between looking at a file and writing it**: another program that saves between
  the check and the write of a save is overwritten, and a file made by another program
  between the look and the write of `create` or of a copy is replaced (A138). Closing it
  needs locking, which is not attempted.
- **"Open theirs" has the same kind of gap** (A159): the file can change between the look
  that says it is readable and the opening. Then no document is open; the screen says so
  and the next start offers to put the file aside. And a file that goes back to exactly
  what this document last read, between the save that failed and the choice, is written
  with this document when it is let go of (A161; it is refused when the keeper knows of no
  change by another program). Both need a new call in the bridge: one that reads the file
  again into the document a handle holds, or lets go of a document without saving.
- **A step that a screen asks for after "open theirs" was chosen** lands, call by call, on
  whichever document is open when its turn comes (A161). Steps begun before the choice
  are waited for; `Keeper.opens` tells a screen that the document is another.
- ~~**The cross after the app was away** leaves the text in the redo history, loses what
  could be redone, and could take back a second screen's command~~: closed by plan step 1.
  An editing is a group that the cross cancels exactly, and a second writer is refused
  while it holds something (A170, A171, A177).
- **Text that is held when the app is ended is in the file without having been said yes
  to** (A145, A177): the next start has it in the cell, with no editor, no group and no
  history, so it cannot be taken back. That is the choice of A145 (half a sentence is not
  lost); a draft that survives being ended without being in the document is not built.
- **An editing that a screen forgets while it holds something keeps every other change
  out** until the document is closed (A177): the keeper refuses them loudly, and nothing
  ends the group for the screen. And a screen that opens its editing only as it goes
  loses the text behind the close. Both are rules for a screen (`../../AGENTS.md`), not
  enforced.
- **Two changes far apart in one editing lose the styles between them** (A169): the
  editor hands over a text, not keys, and the difference of two texts is one range. Text
  that is held has its styles in the document while the editor shows it plain.
- **A screen that goes with text in its editor that the core refuses** has no one to say
  so to: the text is lost without a word (`GridScreen.dispose`). In the app that is only
  when the app is torn down.
- **A file changed by a program that keeps length and modification time** is not seen as
  changed (A138), and file systems with coarse or late-settling times (FAT, network
  folders, Android's shared storage), where one's own save might later read as changed,
  were not looked at.

What a developer will run into:

- **The set of open files lives in the Rust library for the life of the process** (A141),
  so it survives a Dart hot restart: the document that the restarted Dart code no longer
  holds stays claimed until its old handle is collected, and the app starts with
  "AlreadyOpen". The start screen then offers "Try again" and not to put the file aside.
- **An unreadable document at start** has a way out (A156, A163); what is put aside stays
  in its `put-aside-…` folder for ever, since nothing lists or removes those.
- **A read of a stage costs in proportion to its answer, and a large one is slow** (plan
  step 1; "The read a screen draws from" above): 54 to 78 ms for a root of 1,000 cells
  that all hold grids, on a desktop, nearly all of it in the core's shapes, and a
  document read from a file about a third slower there than the same document built in
  memory (48 to 58 ms against 35 to 41 for the core's part), which is not explained. A
  screen reads again after every change. The way out that exists is a window of rows
  (`phoneWindowAsk`), which no screen uses yet; there is no window of columns in it, no
  read of only the cells a change touched, and nothing was measured on a phone.
- **Reports and grid reads copy IDs and texts** (the first review's finding 9, which it
  suspected and did not measure). A report is lists of 36-character IDs, and reading a
  grid copies every text of it; the stage reads its grid again after every change, and
  one more grid for each level of the trail that the change renamed. What was measured,
  on the 101,001-cell document in a profile build on Linux desktop: reading the root grid
  of 1,000 cells takes 2.8 ms and an inner one of 100 cells 1.5 ms, end to end from Dart.
  A report that names tens of thousands of cells was not measured. Nothing was changed.
- **Arguments are decoded on the calling thread** (A127): Dart writes them and Rust reads
  them inside the call before the work is handed over. For an import of 100,000 cells the
  evaluation measured 34 to 130 ms of the caller's time, of 464 to 736 ms in all. So much
  data belongs in a call that takes a path or bytes.
- **Error messages are English only**: the core's text, shown as it is, with no reason a
  program can read beyond the kind of the error. The app's own sentences are English too
  and are not prepared for translation.
- **CI**: the bridge is not built for iOS; the Android job compiles it with rustup's
  `stable`, not the pinned version (A131); actions are pinned by tag, not by commit.
- ~~**`UI_SPEC.md` contradicts the core about line breaks**~~: settled by the owner. Cell
  text may hold line breaks (A174); the ↵ key of section 7 is real, and the editor has
  the means for it (`CellEditor.insert`, A180). No screen has the key yet.
- **Tests bound by time in `crates/wombat-core/tests/formulas_limits.rs`** can fail when
  the machine is heavily loaded; the one bound by memory was moved to a file of its own
  (`formulas_memory.rs`).
- **The bridge check assumes the shape of the example** (`demo.dart` takes the third cell
  of the root and the first cell inside it); on another document it would show a range
  error as text.
- **Four queues are nested on the Dart side** (the screen's actions, the stage's steps, the
  keeper's calls, the session's calls; A155). A piece of work that asks its own queue, or
  a queue that is waiting for its own, is refused at once (A154, A160), but nothing checks
  at compile time that each asks only the one below. The refusal also meets work that a
  piece started and does not wait for, unless that is a timer or set apart; and a wait for
  ever that goes through a timer's callback is not seen (A160).
- **An error of work in a queue that an `async` function passed on and nobody listened
  to** goes to the zone, not to the queue's owner (A160). `InTurn.post` is the way to do
  work for no one.
- **`Stage`, the keeper and the screens are tested on a stand-in for the core as well as
  on the core.** The stand-in (`app/test/fake_document.dart`) knows two commands,
  `retype`, groups, the stage read, the view state and three states of its file, and a
  test holds it to the real core in those (A179). It knows no styles, links, tags or
  formulas, and no command that makes or removes a cell; what depends on those is tested
  on the real core. A panic of the real core reaching Dart has no test (A129).
- **Two screens on one document** are what `Keeper` is for, and nothing uses it that way
  yet. With two, the view state has one level that is shown (the one gone to last), and a
  reader whose stage disappears goes to that level, whichever screen's it was (A176).
- **What the fourth review's G7, G8 and G9 left** (each is under "Fixes after review" and
  in the items above; plan step 1 changed none of them): a step that a screen asks for
  after "open theirs" was chosen lands, call by call, on whichever document is open when
  its turn comes (G7); the refusal of a wait for ever does not see one that goes through
  a timer's callback, and meets work that a piece merely started (G8); and a file that
  goes back to exactly what the document last read, between the save that failed and the
  choice, is written when the document is let go of, which needs a call in the bridge
  that lets go without saving (G9). For G7, an `Editing` and a `StageReader` now end or
  start again with the document, so an editing's calls cannot land on the other one;
  plain `Keeper.apply` still can.
- **Noticed in the core during plan step 1, and not done**: `links/transfer.rs` and
  `wombat-search/src/replace.rs` roll a failed group back by ending it, undoing it and
  emptying the redo history, which loses what could be redone and cannot roll back when
  the history limit is 0; `cancel_group` would be exact. `wombat edit` has `begin` and
  `end` and no `cancel`, and marks the view state as changed only when the number of
  folds changed, where `apply_changes` now says so itself. `ViewState.selection`
  (TreeSheets' rectangle, filled by the importer) and what a level remembers
  (`selected`) both exist; the bridge uses only the second. The core's own list of
  modules (the comment at the top of `crates/wombat-core/src/lib.rs`) still says "view
  state (folds, selection, zoom)" and that `edit` is "the only way to change a document"
  where it now also reads for an interface.
- **The view state's file is found by the document's ID, not by its path** (A173): two
  files with one document ID in one folder (a file copied by hand) share one, and the one
  written last wins.
- **A level gone to and nothing else changed is written only when the app is put away or
  closed** (A178): an app that is killed without either starts one level off.
