# Milestone 4: links and backlinks

Status: finished, with the limits listed under "Left out, or doubtful". All checks pass
(`cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
`cargo test --workspace`): 259 tests and 1 that only runs by hand (38 of them new), in about 100
seconds. `cargo check -p wombat-core --target wasm32-unknown-unknown` passes. Decisions
A50-A56 and B40-B43 are new. The file format of documents did not change.

The work was interrupted once by a restart of the machine; nothing was lost, and everything
below was run after it.

## What was built

- **Resolution** (`crates/wombat-core/src/links/mod.rs`, `LinkIndex::resolve`). A link
  points at a cell of its own document, a cell of another document (found by the document's
  ID, whatever its file is called), something external, or nothing. "Nothing" says why: no
  such document, no such cell, an ambiguous document or cell, or a link without a target.
  `links::place` gives a cell's text and its location trail (the texts of the cells around
  it, from the root down), which is what an interface needs to show a target.
- **Backlinks** (`LinkIndex::backlinks`): for a cell, every link that resolves to it, from
  all documents: the document and cell that have the link, the range, the linked text.
  Also `outgoing` (all links of a document with what they point at), `broken` and
  `broken_in`.
- **The link index** (`LinkIndex`), built from documents and then kept up to date from the
  change report of every command, undo, redo and group (`LinkIndex::apply`), looking only
  at the cells the report names.
- **The index of a whole workspace** (`crates/wombat-core/src/scan.rs`, `scan::link_index`),
  including documents nobody has open, with an optional cache on disk.
- **Three commands** (`edit/paste.rs`; 41 now): `PasteCells` (copy a cell with all in it
  from any document), `AdoptCells` and `ReleaseCell` (the two halves of a move between
  documents). `links::copy_between` and `links::move_between` use them.
- **Warnings before deleting**: `LinkIndex::would_break` (cells) and `would_break_document`.
- **Imported links without a target**: `links::unknown_links`, `links::resolve_unknown`.
- **Command-line tool**: `wombat links`, `backlinks`, `broken`, `copy-cell`, `move-cell`;
  in `wombat edit`: `link ... cell-in FILE CELL` and `resolve-unknown`.

## How to try it

From `wombat/`, after `cargo build`. Two documents; a cell of one links to cells of the
other; the target is renamed, moved, sorted around, has its neighbours wrapped and its grid
turned, and is then moved into the other document. The link follows every time.

```sh
mkdir -p /tmp/m4 && W=$PWD/target/debug/wombat && cd /tmp/m4
printf 'Shop\n  Fruit | Price\n  Apple | 1.20\n    red\n    green\n  Pear | 2\n  Fig | 3\n' > shop.txt
printf 'Notes\n  see the apple here\n  and green\n' > notes.txt
$W new shop.wombat --from shop.txt
$W new notes.wombat --from notes.txt
printf 'insert-rows / 3 1\nlink /1,1 8 5 cell-in shop.wombat /1,2\nlink /1,2 4 5 cell-in shop.wombat /1,2/1,2\nsave\n' | $W edit notes.wombat --script -
printf 'link /1,3 0 4 cell /1,2\nsave\n' | $W edit shop.wombat --script -
$W links notes.wombat
$W backlinks . shop.wombat /1,2
printf 'text /1,2 "Bramley apple"\nmove-rows / 2 1 4\nsort / 1 2 3 desc\nwrap / 1 2 2 2\ntranspose /\nsave\nshow\n' | $W edit shop.wombat --script -
$W links notes.wombat
$W backlinks . shop.wombat /3,1
$W move-cell shop.wombat /3,1 notes.wombat /1,3
$W links notes.wombat
$W links shop.wombat
printf 'remove-grid /1,3\nsave\n' | $W edit notes.wombat --script -
$W broken . --cache
```

What it printed here, in part. Before the changes:

```text
/1,1 "see the apple here" [8+5 "apple"] -> shop.wombat /1,2 "Apple" (in: "Shop")
/1,2 "and green" [4+5 "green"] -> shop.wombat /1,2/1,2 "green" (in: "Shop" > "Apple")
```

After renaming, moving and restructuring (the cell is now in column 3, row 1):

```text
/1,1 "see the apple here" [8+5 "apple"] -> shop.wombat /3,1 "Bramley apple" (in: "Shop")
shop.wombat /3,1 "Bramley apple" (in: "Shop")
2 links to it
  notes.wombat /1,1 "see the apple here" (in: "Notes") [8+5 "apple"]
  shop.wombat /2,1/1,1 "Pear" (in: "Shop" > "") [0+4 "Pear"]
```

After the move into `notes.wombat`, and then after deleting the grid that held "green":

```text
/2,1/1,1 "Pear" [0+4 "Pear"] -> notes.wombat /1,3 "Bramley apple" (in: "Notes")
notes.wombat /1,2 "and green" (in: "Notes") [4+5 "green"] -> BROKEN: there is no cell 0569... in notes.wombat
```

`--cache` keeps the index in `.wombat-index/links.idx`; delete that folder at any time.
Without `--cache` the three commands write nothing.

## The index, and how it is kept up to date

Per document (`DocLinks`): the IDs of its cells, and for each cell that has links, the links
with their range, linked text and target. Over all documents: a table from the ID of a
target cell to the cells that link to it. That is all. It does not hold the order or place
of cells or the text of targets (those are read from the document when shown), because they
could not be kept up to date at a cost that depends on the change only.

After a command the editor returns the cells that were changed, created and removed (A35).
`LinkIndex::apply` takes the old links of the changed and removed cells out of the table,
reads the links of the changed and created cells from the document, and adjusts the set of
cell IDs. Cells that only moved are not named in the report and need nothing. Undo, redo and
groups return the same kind of report and are followed the same way.

It is a disposable copy (A13): an index rebuilt from the documents is equal to it, which is
what the tests check after every step.

## The workspace, and the cache

`scan::link_index` reads every document of the folder, one at a time, and keeps only its
summary, so memory is one document plus the index, not all documents. An interface keeps
the result and follows the documents it edits with `apply`.

With the cache on, the summaries are also written to `.wombat-index/links.idx`. On the next
scan each document file is still **read** (to compute a checksum of its bytes) but only
**parsed** if no cache entry has that length and checksum. So nothing depends on
modification times: a file rewritten with the same length and the same time stamp is
noticed (tested). The cache file starts with a line that holds the length and checksum of
the rest; if that line is not exactly right, the whole cache is ignored and rebuilt.

Measured on this development container, 200 documents of 1,002 cells each (200,400 cells,
20,000 links, 22 MB of files), one run each:

| | Debug build | Release build |
| ---- | ---- | ---- |
| Build the index, parsing every document | 1.94 s | 0.48 s |
| Build it again from the cache | 0.37 s | 0.078 s |
| Build it again after one document changed (parses 1, rewrites the cache) | 0.59 s | 0.11 s |
| Resolve all 20,000 links | 12 ms | 4.7 ms |
| Backlinks of one cell | 6 µs | 1.3 µs |

Memory: the process held 6.7 MB before and 34.2 MB after building, with a peak of 47.7 MB.
The 27.5 MB difference is an upper bound for the index, not its size: it includes memory
the allocator kept after the documents were dropped. Holding all 200 documents in memory at
once would take several hundred megabytes. The cache file is 8.2 MB, most of it the cell
IDs (32 characters each).

One edit of a linked cell, with the index following (2,000 edits each):

| | 1,002 cells | 100,002 cells |
| ---- | ---- | ---- |
| Command and index together, debug | 13.1 µs | 14.5 µs |
| The index's part, debug | 3.1 µs | 3.9 µs |
| The index's part, release | 0.33 µs | 1.09 µs |

A hundred times the cells costs the index between 1.3 and 3.3 times as much (the larger
hash tables no longer fit the processor's cache), not a hundred times. The test fails if it
is over ten times plus 20 µs.

## The rules that were chosen

**Deleting a target** (A55, B42). The link stays in the text and is reported as broken.
No other cell and no other document is rewritten. Undoing the deletion makes it resolve
again, because the cell comes back with its ID. `would_break` lists, before a deletion, the
links that it would break.

**Deleting a document.** Links into it are broken ("no such document"). The same holds for
a document that is simply not in the folder.

**Ambiguity** (A50). Two files with one document ID (a file copied by hand): only the first
by name is indexed, both are listed as duplicates, and a link into that document from any
other document is reported as ambiguous instead of being resolved to either file. A
document's links to its own cells still resolve within it. A cell that is not where its
link says and exists in several documents is also ambiguous.

**A cell that moved to another document** (A50). A link is first looked for where it says.
Only if the cell is not there is it looked for by ID in the other documents; found in
exactly one, the link resolves and is marked "moved". This is not a guess: cell IDs are
unique across documents by decision A5, and where they are not, the result is "ambiguous".

**Copy between documents** (A51). The pasted cell keeps its own ID; the cells inside get new
ones. Links inside the copy to cells that were copied with it point at the copies. Links to
other cells of the source document keep pointing at those cells and now name that document.
Links to cells of the document they arrive in no longer name a document.

**Move between documents** (A51, A52). The moved cells keep their IDs. In the source, links
to them now name the target document; in the target, links to them no longer name a
document; links between the moved cells are unchanged. Links from third documents are not
touched and resolve as "moved" until `LinkIndex::repairs` corrects them.

The move is **one unit of undo in each document, not one unit overall**: an editor edits
one document, and there is no history above documents. `move_between` does both halves or
neither. Undoing both gives both documents back exactly (tested, also at random). Undoing
only one leaves the cells in neither document or in both until the other is undone; nothing
is lost, and both states are reported correctly (broken links, or shared IDs). An interface
should offer the two undos as one action. This is the part of the milestone I would look at
first if something seems wrong.

## TreeSheets' six link actions

| Action | In TreeSheets | In Wombat |
| ---- | ---- | ---- |
| `A_BROWSE` | Follows the link at the cursor (or the first of the cell): jumps to the cell, or opens the browser. Without a link, opens the text of each selected cell in the browser | `links::link_at` picks the link by the same rule; `LinkIndex::resolve` says what it points at; `links::external` says whether an external target is a URL or a file. Opening anything is the interface's (B40) |
| `A_BROWSEF` | Opens the file that the cell's text names | The interface passes the text to `links::external` and opens it; the core opens nothing (B40) |
| `A_LINK`, `A_LINKREV` | Jumps to the next or previous cell with the same text | Not built: finding cells by text is search, milestone 6 (B41). The ID equivalents exist: a link's target, and a cell's backlinks |
| `A_LINKIMG`, `A_LINKIMGREV` | Jumps to the next or previous cell with the same image | Not built: milestone 6, as a filter on the image's file name (B41) |

So two are covered by functions the interface calls, and four are listed for milestone 6.
None became a command, because none changes a document.

## Tests

259 pass; 38 are new, in six files. (The brief for this milestone said 226 before; counted
the same way as now, 221 passed before.)

- **21 unit tests** (`links/tests.rs`): resolution of every kind, trails, backlinks and
  their order, deletion and undo, the warnings, both kinds of ambiguity, the cache form of a
  summary and 11 ways to spoil it, copy and move between documents link by link, refused
  moves, the six actions' functions, imported links.
- **"A link survives"**, by example: 36 cases over 22 commands, each with a link from the
  same document and one from another. Where decision A41 says the target keeps its ID, both
  links must resolve to it afterwards; where it says the cell goes (the repeated first cell
  in hierarchify, the second of two cells that merge in a hierarchy swap, deleted rows,
  columns and grids), both must be broken; undo must restore both.
- **The main rule, at random** (`tests/links.rs`, `tests/support/links.rs`): one to three
  documents, 400 cases each of up to 50 steps: any of the 38 older commands, links across
  documents (also to missing cells and documents), groups, undo, redo, copies and moves
  between documents, repairs. After every step the index that followed the reports must
  equal an index built from the documents. After every single command, every link whose
  target cell still exists must resolve to it and be among its backlinks, every link whose
  target is gone must not, and undo and redo must give the earlier and later index exactly.
  At the end everything is undone and every document must equal its original.
  A fixed run of 250 cases prints what happened: 3,483 commands, 10,569 link checks that
  found the target alive and 100 that found it gone, 976 copies, 791 moves, 107 repairs.
- **The same on imported files** (`wombat-cts/tests/links.rs`): all 51 `.cts` files, two and
  three at a time.
- **Do the tests bite?** The index update was broken on purpose in four ways (forgetting
  removed cells, created cells, changed cells, or the backlink table). Each made the random
  tests fail. This shows they are not empty, not that they are complete.
- **Workspace and cache** (`tests/links_workspace.rs`, 5 tests): documents that are not
  open, renamed, deleted and added; a changed file with the same length and time stamp;
  a deleted cache file and folder; 12 kinds of damage; every third byte of the cache file
  flipped in turn (each time the result must be the index that reading the documents gives,
  and a good cache must be written again); a folder that cannot be written to; duplicates.
- **Size** (`tests/links_large.rs`): the numbers above, with generous bounds.
- **Command-line tool** (`wombat-cli/tests/links.rs`, 4 tests): the demo, broken links,
  duplicates, copy and move, refusals that leave both files untouched, imported links.

## What milestone 6 should reuse

- **`summary::Summary`**: implement it for what search keeps per document (`of`, `update`
  from a change report, `encode`, `decode`). `links::DocLinks` is the worked example.
- **`scan::scan::<S>`**: gives one summary per document of a folder, reading each file
  once, with the cache (`.wombat-index/<kind>.idx`), stale detection and damage handling
  already done. It is generic; only `scan::link_index` is about links.
- **The test pattern**: `tests/support/links.rs` runs random edits over several documents
  and compares "followed the reports" with "built from scratch". A search index needs the
  same comparison.
- One difference to expect: search will need cells' texts and probably their trails. A
  trail changes when an ancestor is renamed, and the change report names only the renamed
  cell. So either trails are computed when results are shown (as here), or the summary
  must find the cells below a changed cell, which is no longer O(change).

## Left out, or doubtful

- **Reading a file to check it is not free.** Every scan reads every document file in
  full. That is what makes the cache trustworthy, and it is why a cached scan still takes
  0.08 s for 22 MB. A faster mode that trusts sizes and time stamps was not built.
- **The cache is safe against damage, not against forgery.** Its checksum is not
  cryptographic. Someone who writes a cache file on purpose can make the index wrong.
- **The memory figure for the index is an upper bound**, as said above; I did not measure
  its exact size.
- **Only 12 links exist in the 51 imported `.cts` files**, 2 of them without a target. The
  importer's links are covered, but thinly; the random tests add their own links.
- **Backlinks are in ID order**, which is fixed but means nothing to a reader. The
  command-line tool sorts by file name and document order by loading the documents.
- **Correcting a link drops its unknown fields** (move, `repairs`, `resolve_unknown`),
  because `SetLink` makes a new link. A link's range can also merge with a neighbour that
  has the same target.
- **`move_between` reads both documents whole** to find the links to correct: its cost is
  that of the documents, not of the moved cells. It does not use the index.
- **A move cannot be taken back if the target editor keeps no history** (history limit 0)
  and the second half fails; then the first half stays done.
- **The three new commands are not in the older random tests** (`tests/commands.rs`),
  which need one document. They are in the new ones, with the same checks of change report,
  size bound and undo.
- **Links are not followed into unknown fields**, and IDs written there are not rewritten
  on copy (as in A28).
- **`wombat links` and `backlinks` load target documents to show texts and trails**: fine
  for a tool, but an interface showing many backlinks would want that cached; milestone 6
  is the place.
- **Not compared with the real TreeSheets.** TreeSheets has no cell IDs and no backlinks,
  so there is nothing to compare; `link_at` and `external` follow its C++ by reading only.
- **Three small changes to existing code** besides additions: `Document`'s cell check and
  `Workspace::names` became visible inside the crate, `Editor` got `in_group` and
  `clear_redo`, and the command-line tool's cell naming moved to a function so that the new
  commands can use it.
