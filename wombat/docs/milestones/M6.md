# Milestone 6: the search service

Status: finished, with the limits listed under "Left out, or doubtful". All checks pass
(`cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
`cargo test --workspace`): 300 tests and 2 that only run by hand (41 of them new; 259 before), in
2 minutes 15 seconds. `cargo check -p wombat-core -p wombat-search` passes for
`wasm32-unknown-unknown`, `aarch64-linux-android` and `aarch64-apple-ios`. Decisions A70-A79
and B60-B65 are new. The file format of documents did not change; the layout of the index
cache did (section 7 of `FILE_FORMAT.md`).

Besides search, this milestone repaired the cache of milestone 4, which a review found
unsafe and unfit to carry a text index ("The cache, repaired" below).

## The engine: not Tantivy (decision A70)

The plan left open whether the Tantivy library suits phones and the web. It was tried
first (version 0.24, default features off), and the answer is no:

| | Tantivy | What was built |
| ---- | ---- | ---- |
| Web (`wasm32-unknown-unknown`) | does not build: `getrandom` and `uuid` need their `js` feature, which ties the build to a browser; its writer wants threads, its index a directory | builds |
| Phones (`aarch64-linux-android`, `aarch64-apple-ios`) | does not build here: `zstd-sys` is C code and needs the phone's C toolchain | builds, Rust only |
| Crates added | 119 (127 for the web) | 2 (`unicode-normalization`, `tinyvec`) |
| Time to check from nothing, four cores | 19 s (43 s of processor time) | 3.5 s for the search crate with the core and all they need |
| Size, stripped | 4.2 MB for a program that indexes one sentence | 2.3 MB for the whole `wombat` tool, search included |
| Match on part of a word, and in text without spaces | only with an n-gram tokeniser set up for it | what it does |
| One keystroke in one cell | delete, add, commit a segment | 3 µs, in place |

It would probably build for phones on a machine with the Android and Apple toolchains; that
was not tried, because the other rows decide it. The engine is `crates/wombat-search`:
about 4,150 lines with its unit tests, no threads, no files (the folder is read through `wombat_core::scan`).

## What was built

- **The index** (`index.rs`, `engine.rs`): per document, every cell's texts as they are
  and folded, where it is, and the properties that filters ask about; kept up to date from
  the change report of every command, undo, redo and group (`SearchIndex::apply`).
- **Folding** (`fold.rs`): the form in which text is compared.
- **Queries** (`query.rs`): a `Query` value that an interface can build, and a text syntax
  that parses into it.
- **Search** (`SearchIndex::search`): ranked results with field, highlight ranges, snippet
  and location trail; paging; and `SearchIndex::next_match` for "find next".
- **The reference** (`naive.rs`): the same answers by reading every cell, with the plainest
  code that could be right. The tests hold the index to it.
- **Replace** (`replace.rs`): find and replace as one undoable step per document.
- **The workspace** (`workspace.rs`): the index of a folder, documents open or not, with a
  cache on disk.
- **Command-line tool**: `wombat search`, `wombat replace`, `wombat import-all`; in
  `wombat edit`: `replace-all` and `find`.

## What is searched, and how matching works

Searched: the **text** of a cell, its **note**, the file name of its **image**, the
**targets of its links** (web addresses and file paths), and the **text of the cells its
links lead to**, in every document of the workspace, open or not. Tag names are searched
because a tag is a cell's text; a tag that no cell uses is not a result (results are
cells).

A word matches if it is found **anywhere** in one of those, compared in folded form:

| Typed | Finds | Why |
| ---- | ---- | ---- |
| `app` | Apple, Pineapple | any part of a word, so every keystroke narrows |
| `APPLE`, `ＡＰＰＬＥ` | Apple | case and full-width forms are ignored |
| `cafe`, `CAFÉ` | Café | accents of Latin and Greek letters are ignored |
| `strasse` | Straße | `ß` is `ss`; the highlight is on the `ß` |
| `istanbul`, `ıstanbul` | İstanbul | the four Turkish i's are one letter |
| `σισυφοσ` | ΣΊΣΥΦΟΣ, Σίσυφος | final sigma, accents |
| `ガイド` | ｶﾞｲﾄﾞ | half-width forms |
| `本語`, `索`, `텍스트` | 日本語のテキスト, 中文搜索, 한국어 텍스트 | text without spaces: any part, one character included |
| `o` | not `ø`; `か` not `が`; `и` not `й`; `е` not `ё` | only accents that Unicode holds as separate marks on Latin and Greek letters are ignored |

Several words must all be found (in any field, in any order). `"quoted words"` must be
found together. `-word` must not be found. `OR` (or `|`) between words means either.
`case:Word` must be found exactly as written.

## The query syntax

```text
apple pie              both words
"apple pie"            the phrase
apple OR pear          either; also: apple | pear
-apple                 not
(a OR b) -c            brackets
case:Apple             exactly these characters (case:"Two Words")

tag:NAME               cells whose text is the tag NAME, in documents that have that tag
has:tag                cells whose text is any tag of their document
has:note  has:image  has:grid  has:link  has:text
has:broken-link        cells with a link that points at nothing
in:ID                  the cell with this ID and everything inside it (a branch)
doc:NAME               the document NAME (with or without .wombat, any case)
links-to:ID            cells with a link that leads to this cell
linked-from:ID         cells that a link of this cell leads to
edited:7d              edited in the last 7 days (m minutes, h hours, d days, w weeks)
edited:2026-01-31      on that day (UTC)
edited:2026-01-01..2026-01-31     between; either end may be left out
recent:5%              the most recently edited 5% of each document
kind:data|code|var_assign|var_read|view_h|view_v|formula
bg:#rrggbb             background colour          fg:#rrggbb   text colour
style:bold+italic      exactly this style (bold italic fixed underline strike); style:none
text:"exactly this"    cells with exactly this text
image:FILE             cells that show this image
sort:relevance | recent | relevance-recent | document
```

A query with only filters is a query: `tag:todo edited:7d sort:recent` is "everything
tagged todo that was edited this week, newest first". An empty query is every cell.
A quote or bracket left open is closed at the end, so a half-typed query still searches.
A filter with a value that means nothing is an error that says what would (`has:wings`).
A word with a colon that is not one of the filters (`https://example.com`, `12:30`) is a
word. The core never reads the clock: `parse(text, now)` is given the time.

As a value: `Query::{All, Term, Filter, And, Or, Not}` with `Term { text, exact }` and
`Filter::{Tag, Has, LinksTo, LinkedFrom, Edited, Recent, Doc, DocName, Within, Kind,
CellColor, TextColor, Style, TextIs, Image}`.

Limits, so that no query can take unbounded time or memory (decision A75): 4,096 bytes,
64 words and filters, nesting 16 deep, 1,024 bytes a word. There is no pattern language;
finding is plain substring search.

## The ranking rule

Every word of the query that is not negated gets points for its best match in the cell;
fewer is better:

- 4 x the field: text 0, displayed result 1 (milestone 5), note 2, text of a linked cell 3,
  image name 4, link target 5;
- plus the kind of match: the whole field 0, a whole word 1, the start of a word 2, inside a
  word 3. In text without spaces every character counts as a word.
- A word that is not in the cell at all, which `OR` allows, gets 32.

The points are added up, and results are ordered by: fewer points; then (only with
`sort:relevance-recent`) the later edit; then the shorter text; then the cell nearer the top
of its document; then the document's name; then the order within the document.
`sort:recent` puts the later edit before the points; `sort:document` is name and order
only. Nothing else takes part (no statistics of the workspace), so the order is the same
on every machine and does not shift when other documents change.

For `apple`: `Apple` (whole cell, 0), `apple pie` and `green apple` (a whole word, 1; the
shorter first), `Crab-apple jelly` (1, longer), `Pineapple` (inside a word, 3), then a cell
with the word in its note (9), then a cell that links to `Apple` (12).

## Results

A hit has: the document and cell ID; the field that matched; the content of that field
and the ranges of the matches in it (start and length in code points, in order, never
cutting a user-perceived character); a snippet of at most 80 characters around the first
match, with the ranges within it and whether it is cut at either end; the cell's text;
the **location trail** (the texts of the cells around it from the root down, the same as
`links::place` gives); points, depth and edit time. `Options { order, offset, limit }`
pages through them, and `Results::total` says how many there are.

Trails are worked out when a result is made, not stored (decision A73): renaming or moving
a cell changes the trail of everything inside it at no cost, and they cannot go stale.

On this development container (4 cores; the index uses one), release build, one run. The
workspace is made up (`tests/support/corpus.rs`): 20 documents of 5,000 cells nested four
deep, 99,627 cells, 3.5 MB of text and notes, 12.5 MB of files; words of mixed lengths from
a vocabulary of 20,000 in which a few are common, one cell in twelve in Chinese, Japanese
or Korean, notes on one cell in twenty, tags, links, colours, edit times.

| ---- | ---- | ---- |

| Build it from the folder, parsing every document | 0.40 s | not run |
| Load it from the cache, checking every document's bytes | 0.125 s | not run |

| Cache on disk | 8.6 MB | not run |

The 42 queries are in `corpus::queries`: a word typed letter by letter, common and rare
words, two words, a phrase, OR, NOT, `case:`, Chinese, Japanese and Korean of one to three
characters, a web address, a number, and every kind of filter alone and with a word.

What the numbers say, candidly:

- **Typical queries take under a millisecond** at 100,000 cells: a word of two letters or
  more goes through the table and looks at few cells.
- **The slow ones are the queries that match most cells**: one common letter (`e`, `a`:
  21 to 23 ms), the empty query, and a word marked `case:` (which looks at every cell).
  They look at every cell, score it and sort. That is under the 50 ms target at 100,000
  cells and **over it at a million** (a quarter of a second for one letter). Search is
  linear in the number of cells for such queries; nothing here is parallel.
- **The cache makes opening about three times faster, not thirty.** Reading an entry still
  folds the text and builds the table; only the parsing of JSON is saved. Storing the
  table in the cache would make loading faster and the cache larger; it was not done.
- **The index takes about 8.5 times the text it searches**, which is more than
  "modest": per cell about 96 bytes of record, the text twice (as it is, and folded if that
  differs), an ID table, and the table of character pairs. Before lists of very common
  pairs were dropped it was 10.7 times. A million cells need about 300 MB, too much for a
  phone; a workspace of that size would need the table in a more compact form.
- **Following an edit does not depend on the size of the workspace.**

The test `search_at_size` asserts, in a release build: median under 10 ms, worst under
50 ms, an edit under 0.5 ms, memory under 16 times the text, loading from the cache faster
than parsing; and that a sample of the queries gives exactly what the reference scanner
gives. In a debug build it runs on 20,000 cells with ten times the bounds.

## How the index follows edits

After a command the editor returns the cells that were changed, created and removed, and
the cells whose grids gained, lost or reordered cells (decision A35). The index reads the
changed and created cells again, frees the removed ones, and for each cell whose grid
changed reads the list of the cells directly inside it, to know where they are. So the
cost is that of the cells named **plus the direct children of changed grids**: inserting a
row into a grid of 10,000 rows makes the index look at that grid's cells (not at their
texts), as the command itself does.

The table of character pairs is never searched for stale entries: an edit adds the pairs
that are new, and counts those that went. Because every proposed cell is checked against
its text, a stale entry costs a look and can never produce a wrong result. When half the
table is stale it is built again.

## The cache, repaired (review of milestone 4)

The review found four things in the cache layer that search was to be built on. What was
done about each:

1. **The cache was written through symbolic links** and could overwrite a file outside the
   workspace. Reproduced first with a test that failed on the committed code (`wombat broken
   . --cache` with `.wombat-index/links.idx` a link to another file replaced that file).
   Now the cache folders and files must be real folders and files, or the cache is neither
   read nor written; entries are written to a new temporary file and renamed into place.
   Tested for the link cache and the search cache, in the core and through the tool: a link
   in place of the top folder, the kind's folder, an entry, the temporary file, and the old
   single file.
2. **One JSON file for everything, loaded as a tree, rewritten whole.** Now one entry per
   document (`.wombat-index/<kind>/<file name>.idx`), in a compact binary form whose
   reading takes memory in proportion to its size; an entry over 64 MiB is not read; a
   changed document rewrites its own entry only. Two ways to check (`CacheMode`):
   `Verify` reads every document and compares a checksum, as before; `Fast` goes by length
   and modification time and does not read unchanged documents. The trade-off is stated in
   decision A71: `Fast` misses a file changed with its length and exact time kept, and to
   leave no smaller hole it believes only files that were at least two seconds old when
   their entry was written. The link index uses the same mechanism (its summary is binary
   too now) and its tests pass, rewritten for the new layout where they named the old one.
3. **A summary sees only the document after a change.** The search summary keeps each
   cell's folded text itself, so it can tell which pairs are new; the trait was extended
   only by `fingerprint` (point 4) and by `encode`/`decode` working on bytes.
4. **The first line carried only a version.** It now also carries
   `Summary::fingerprint()`: for search, a number computed by folding fixed samples with
   the rules as they are, so a cache made under other rules is refused without anyone
   remembering to raise a version; a test pins the number. In fact the search cache holds
   no folded text at all (folding happens when an entry is read), so this guards the
   future more than the present. Of the two smaller findings: `LinkIndex::unmark_ambiguous`
   was added; **the second file of a duplicated document ID is still left out of `broken`
   and its counts** (not fixed).

A cache folder of milestone 4 (`.wombat-index/links.idx`) is simply no longer read; it can
be deleted.

before it ends; the replacement is not searched again; the replacement is put in as
written whatever the case of what it replaces; notes are not touched. Differences: B62.

## The hook for formulas

`wombat_search::index::searchable(doc, cell)` is the one place that says what of a cell is
searched; the index and the reference scanner both call it. It returns a `Searchable`
with `text`, `note`, `image`, `urls` and **`shown`: what the cell displays where that is
not its stored text**. It returns `None` for `shown` today. When milestone 5 can compute a
formula cell's result, returning it there is the whole change on the search side: the
field is indexed, matched, ranked (just after the text), highlighted (`Field::Shown`) and
written to the cache already, and a test does all of that with a stand-in
(`a_displayed_result_is_searched_as_a_field_of_its_own`).

One thing milestone 5 must then do: **the change report has to name every cell whose
displayed result changed**, not only the cell that was edited, or the index will keep the
old result for the others. And `links::unknown_links` (B15) still leaves formula cells out
for the same reason; that can be revisited at the same time.

tests now run 200, and 6,400 more were run by hand after the fix without a failure.

This shows that the tests are not empty, not that they are complete: the breakages were
chosen by hand.

## How to try it

From `wombat/`. All of TreeSheets' examples in one folder, searched:

```sh
cargo build --release
W=$PWD/target/release/wombat
rm -rf /tmp/m6 && $W import-all ../TS/examples /tmp/m6 && cd /tmp/m6
$W search . tutorial --limit 4 --time
$W search . grid cell --limit 3 --cache --time
$W search . グリッド --limit 3 --cache --time
$W search . has:tag --limit 5
$W search . '前端 OR 後端' --limit 3
$W search . has:tag doc:tutorial-zh_TW --limit 3
$W search . press --in tutorial.wombat /1,3/2,1 --limit 3
$W search . press --next tutorial.wombat /1,3/2,1
```

## Left out, or doubtful

- **Typing mistakes are not forgiven** (decision A78), nothing is searched by meaning, and
  nothing inside images. All three were on the plan's "out of scope" or "future" lists.
- **Queries that match most cells are linear in the workspace**, and so over the target at
  a million cells (table above).
- **Memory is about 8.5 times the text.** See "Measured".
- **The cache saves parsing, not indexing.** See "Measured".
- **`Fast` cache checking trusts length and time** (decision A71). `--cache=verify` does
  not.
- **Russian `ё` and `е`, `й` and `и` are different letters** to the search, and `ø` is not
  `o`. Only accents that are separate marks on Latin and Greek letters are ignored. The
  Turkish i's are all one letter, which a Turkish reader may not want.
- **Word boundaries are simple**: a word is a run of letters and digits; Chinese, Japanese
  kana, Thai, Lao, Khmer and Burmese characters each count as a word. This only affects
  the order of results, never what is found.
- **Tags that no cell uses are not results.** Results are cells.
- **A tag narrows to the tagged cells themselves.** In TreeSheets a cell has a tag when its
  text is the tag's name, and `tag:todo` finds exactly those cells; it combines with place
  (`doc:`, `in:`), time, links and looks. "Rows that have a todo cell and mention apple" is
  not expressible: `tag:todo apple` asks for one cell that is both, which only a note or a
  link can make true. A filter on what is in the same row would do it and was not built.
- **Of several links, the first that has a word is the one shown** in a result; the points
  are those of the best one.
- **The first search after cells moved pays for working out where the cells are**, per
  document that has a match (about a millisecond for 5,000 cells).
- **A link's target is searched through the link index of the documents at hand.** A link
  into a document that is not in the folder contributes nothing; a link that is ambiguous
  or broken neither.
- **Replace works on text only**, not on notes, link targets or image names, as in
  TreeSheets. Replacing across a folder with the tool is one undo step per document, but
  the tool keeps no history between runs: there it is simply a saved change.
- **Replace can be refused** when the replacement would join up with the text beside it
  into one character (an accent alone as the replacement); then nothing is changed.
- **`wombat search` builds the index on every run** (from the cache if asked). A long-lived
  interface would keep it and follow edits; the tool cannot show that.
- **The second file of a duplicated document ID** is not searched and is still left out of
  the link index's `broken` (review of milestone 4, not fixed).
- **Not compared with the real TreeSheets.** Its search is a text box and a setting; what
  it finds was read from the C++ (`Text::IsInSearch`, `ReplaceStr`, `ApplyEditFilter`,
  `FindLink`), and the differences are B60-B65.
- **The made-up text of the size tests is not real text**: 40 syllables make all its words,
  so pairs of characters repeat more than in a real language, which makes the table less
  selective than it would be. The 51 imported documents are real but small.
- **Changes to existing code outside the new crate**: `scan.rs` rewritten (cache layout and
  safety); `Summary` works on bytes and has `fingerprint`; `summary.rs` got `Writer`,
  `Reader`, `digest`; `DocLinks` encodes to bytes; `LinkIndex` got `sources`,
  `has_cell_links`, `unmark_ambiguous`; `scan::link_index` takes a `CacheMode`; the link
  tests' runner got a hook. In the tool: `links.rs` passes the mode (one line), `main.rs`
  got five lines of dispatch and the help text, `edit.rs` two commands.
